# Research: نسخ احتياطي سحابي (Google Drive شخصي لكل مدرّس)

## 1. نطاق صلاحية Google Drive (scope) — `drive.file` بدل `drive` الكامل أو `drive.appdata`

**القرار**: نطاق `https://www.googleapis.com/auth/drive.file` — التطبيق بيقدر يوصل بس للملفات اللي **هو نفسه** أنشأها (أو المستخدم فتحها بالتطبيق صراحة)، مش أي ملف تاني في درايف المدرّس.

**السبب**: 
- أمان — المدرّس بيوافق على وصول محدود جدًا وواضح (FR-014)، مش "قراءة/كتابة كل ملفاتك".
- تصنيف Google الحالي لـ`drive.file` = نطاق **غير حسّاس (non-sensitive)** — يعني عملية اعتماد التطبيق عند Google أبسط وأسرع من النطاقات الحسّاسة/المقيَّدة (اللي بتحتاج مراجعة أمان (Security Assessment) ممكن تاخد أسابيع ومصاريف). ده فرق عملي كبير لمشروع صغير بينشر مباشرة (APK/Play Store) بلا فريق أمان مخصّص.

**بدائل اتقيّمت**:
- **`drive` (وصول كامل لكل الدرايف)** — رُفض: نطاق حسّاس/مقيَّد، يحتاج مراجعة أمان من Google قبل ما التطبيق يقدر يستخدمه مع مستخدمين حقيقيين بعدد كبير — عملية طويلة ومعقّدة غير متناسبة مع حجم الميزة.
- **`drive.appdata` (مجلد "App Data" المخفي)** — ميزته إن الملفات مش ظاهرة في واجهة درايف العادية للمستخدم (تنظيم أنضف)، لكن Google بتصنّفه أحيانًا كنطاق يحتاج تحقّق إضافي حسب سياق الاستخدام — وميزته (الإخفاء) مش أساسية هنا (المدرّس أصلاً عايز يعرف إن فيه نسخ محفوظة). `drive.file` أبسط اعتمادًا وكافي تمامًا للحاجة.

## 2. طريقة الاتصال بـGoogle Drive API — استدعاءات REST مباشرة عبر `dio`، مش مكتبة `googleapis`

**القرار**: `google_sign_in` للحصول على access token بس، وبعدين استدعاءات HTTP مباشرة لـGoogle Drive API v3 (`POST /upload/drive/v3/files` multipart للرفع، `GET /drive/v3/files` للقائمة، `GET /drive/v3/files/{id}?alt=media` للتحميل، `DELETE /drive/v3/files/{id}` للحذف) عبر `dio` الموجود بالفعل كتبعية.

**السبب**: العمليات المطلوبة أربعة بس (رفع/قائمة/تحميل/حذف) على مجلد واحد بسيط — إضافة مكتبة `googleapis` + `googleapis_auth` (تبعيات كبيرة، مصمَّمة لتغطية كل Google APIs) مبالغة لحجم الاستخدام ده. المشروع أصلاً بيفضّل تبعيات قليلة (راجع `pubspec.yaml` — استخدام مباشر لـ`dio`/`http` في أماكن تانية بدل مكتبات عميلة تقيلة).

**بدائل اتقيّمت**:
- **`googleapis` + `googleapis_auth`** — رُفضت: حجم تبعية أكبر بكتير من الفايدة الفعلية لأربع عمليات REST بسيطة.

## 3. متطلب تشغيلي سابق للكود: إعداد Google Cloud Console (OAuth client)

**القرار**: قبل أي سطر كود في `/speckit-tasks`/التنفيذ، لازم يتعمل (مهمة تشغيلية منفصلة، خارج نطاق الكود، زي إعدادات VPS في specs سابقة):
1. مشروع Google Cloud (جديد أو موجود) + تفعيل Google Drive API.
2. شاشة موافقة OAuth (OAuth consent screen) — بيانات أساسية (اسم التطبيق، شعار، إيميل دعم) + نطاق `drive.file` مُضاف.
3. Android OAuth client ID مربوط بـ:
   - اسم الحزمة: `com.amertimraz.activeclass`.
   - بصمة SHA-1 لتوقيع الـrelease (**مش** SHA-256 الموجود بالفعل في `RELEASE_SIGNING_INFO.md` — لازم تُستخرج بصمة SHA-1 المقابلة لنفس الكيستور عبر `keytool -list` أو `apksigner`).

**السبب**: `google_sign_in` هيفشل بالكامل (خطأ "sign in failed"/"DEVELOPER_ERROR") من غير الإعداد ده — نفس فكرة "بصمة التوقيع" اللي المشروع أصلاً متعوّد عليها (`RELEASE_SIGNING_INFO.md`)، لكن لازم SHA-1 خصيصًا لـGoogle (مش SHA-256 المستخدَم في التحقق من توقيع الـAPK نفسه).

**⚠️ خطر مهم موثَّق صراحة**: لو الإعداد ده ماتعملش بالظبط بنفس بصمة الـrelease الحالية (`5f74fe10af2da396cbf0a98895af02bb5ffbdc01cdf68a55bea25a841f02ec7b` SHA-256، ونظيرتها SHA-1)، تسجيل الدخول هيفشل بس على نسخة الـrelease الموقّعة (ممكن يشتغل غلط على debug بتوقيع مختلف ويدّي انطباع كاذب إن كل حاجة تمام). **لازم الاختبار النهائي يحصل على APK release موقّع بنفس الكيستور** — نفس الدرس اللي اتعلّمناه في جلسة سابقة (حادثة مسح بيانات بسبب توقيع debug مختلف).

## 4. استراتيجية إعادة المحاولة عند فشل الرفع — دالة صرفة منفصلة، بلا لمس `sync_engine.dart`

**القرار**: منطق قرار "نحاول تاني ولا لأ" (زي `sync_retry_policy.dart` من spec 030) بيتكتب كدالة صرفة جديدة مستقلة — حد أقصى محاولات معقول (مثلاً 5) بفاصل متزايد (exponential backoff بسيط)، وبعدها يعتبر الرفع "فاشل" لحد النسخة الدورية الجاية (مش يفضل يحاول بلا نهاية في الخلفية).

**السبب**: الميزة دي مستقلة تمامًا عن `SyncEngine`/مزامنة وضع الفريق — خلطها فيه هيعقّد كود شغّال ومُختبر بالفعل بلا داعٍ. نفس مبدأ الفصل بين `BackupService` و`sync_engine.dart` الحالي (مفيش تداخل).

**بدائل اتقيّمت**:
- **إعادة محاولة لا نهائية حتى النجاح** — رُفضت: ممكن تستهلك بطارية/بيانات إنترنت بلا داعٍ لو الحساب اتلغى ربطه فعليًا (FR-006 بيطلب حد واضح).

## 5. تجديد access token — `signInSilently()` قبل كل عملية، مش تخزين توكن طويل المدى يدويًا

**القرار**: `google_sign_in` بيدير تجديد الـaccess token تلقائيًا داخليًا (الـrefresh token بيتخزّن بأمان بواسطة المكتبة نفسها على مستوى نظام التشغيل) — كل عملية رفع/قائمة/تحميل/حذف تستدعي `GoogleSignIn.instance.signInSilently()` (أو المكافئ) الأول للتأكد من توكن صالح، بدل ما التطبيق يخزّن/يجدّد التوكنات بنفسه يدويًا.

**السبب**: أبسط وأأمن — إعادة تطبيق منطق تجديد OAuth يدويًا عرضة للأخطاء وغير ضروري، المكتبة الرسمية مصمَّمة بالظبط لده.
